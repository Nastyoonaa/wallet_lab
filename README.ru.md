# Wallet Lab

[English](README.md) · **Русский**

Wallet Lab — портфолио-проект о восстановлении денежного перевода после обрыва сети или перезапуска приложения. Проект симулирует переводы в рублях между двумя тестовыми кошельками. Начальный баланс Алисы — 1 000 ₽, Боба — 250 ₽. Все суммы в API передаются целым числом копеек.

Приложения для Android и iOS используют общий модуль Kotlin Multiplatform и один экран Compose Multiplatform. Бэкенд на FastAPI хранит переводы в PostgreSQL.

## Быстрый запуск

Установите Docker Compose и выполните команды из корня репозитория.

```sh
docker compose up --build -d
curl -fsS http://localhost:8000/wallets
```

[Интерактивная документация API](http://localhost:8000/docs) содержит схемы запросов и ответов. Контейнер API применяет версионированные SQL-миграции перед запуском. Начальные данные добавляются один раз для каждой базы. Перезапуск Compose сохраняет балансы и историю переводов.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET | `/wallets` | Список кошельков и их балансов |
| GET | `/wallets/{wallet_id}` | Баланс кошелька |
| GET | `/wallets/{wallet_id}/history` | История от новых переводов к старым, с суммой со знаком |
| POST | `/transfers` | Отправка или повтор перевода с UUID в заголовке `Idempotency-Key` |

При успешной отправке и повторе API возвращает HTTP 201 и исходный результат с тем же ID перевода и временем создания. Тот же ключ с другим допустимым телом запроса возвращает HTTP 409 и код `idempotency_conflict`. Сервер также сохраняет результат отказа по бизнес-правилам для конкретного ключа и тела запроса. Для нового перевода нужен новый ключ. При ошибке валидации API возвращает HTTP 422 до сохранения ключа.

## Запуск мобильных приложений

Запустите API в деморежиме из корня репозитория.

```sh
WALLET_LAB_DEMO=1 docker compose up --build -d
```

| Платформа | Настройка и запуск |
| --- | --- |
| Android | Установите JDK 17+ и Android SDK Platform 37. Откройте `mobile/` в Android Studio и запустите `androidApp` в эмуляторе. Можно выполнить `./gradlew :androidApp:installDebug` из `mobile/`, а затем открыть Wallet Lab. Адрес API из эмулятора — `10.0.2.2:8000`. |
| iOS | На Mac с Apple Silicon, Xcode, iOS Simulator и JDK 17+ откройте `mobile/iosApp/WalletLab.xcodeproj`. Выберите схему WalletLab и симулятор iPhone. Xcode запустит Gradle Wrapper для сборки общего фреймворка. Если Xcode не находит Java, задайте `JAVA_HOME` в терминале и выполните команду ниже. Адрес API из симулятора — `127.0.0.1:8000`. |

Команда сборки для iOS из корня репозитория на macOS.

```sh
xcodebuild -project mobile/iosApp/WalletLab.xcodeproj -scheme WalletLab \
  -configuration Debug -destination 'generic/platform=iOS Simulator' \
  -derivedDataPath mobile/iosApp/DerivedData ARCHS=arm64 CODE_SIGNING_ALLOWED=NO build
```

Установка и запуск на уже загруженном симуляторе.

```sh
xcrun simctl install booted mobile/iosApp/DerivedData/Build/Products/Debug-iphonesimulator/WalletLab.app
xcrun simctl launch booted lab.wallet.ios
```

## Мобильное демо за 60 секунд

1. Начните с исходных балансов. У Алисы 1 000 ₽, у Боба 250 ₽. Откройте Wallet Lab на Android и выберите Alice.
2. Введите `150` в поле **Сумма, ₽**, включите **Демо: потерять ответ** и нажмите **Перевести**. Сервер фиксирует перевод и задерживает ответ на пять секунд. Клиент ждёт две секунды и показывает **Не удалось подтвердить статус**.
3. Принудительно остановите приложение командой `adb shell am force-stop lab.wallet.android`, затем снова откройте Wallet Lab. На экране появится сохранённый перевод с той же суммой и получателем.
4. Нажмите **Проверить статус**. В подтверждении отобразится исходный ID перевода. У Алисы останется 850 ₽, у Боба будет 400 ₽. В истории каждого кошелька появится по одной записи с этим ID.

Указанные суммы рассчитаны для свежей базы. Команда `docker compose down -v` удаляет том базы и всю историю демо. Для восстановления исходных данных после сброса снова запустите Compose.

## Восстановление перевода через HTTP

Начните с исходных балансов и включите задержку ответа после коммита.

```sh
WALLET_LAB_DEMO=1 docker compose up --build -d
```

Перед первой отправкой сохраните ключ и тело запроса в файлах. В этом примере файлы имитируют постоянное хранилище мобильного клиента.

```sh
pending=$(mktemp -d)
printf '%s\n' "$pending"
uuidgen > "$pending/key"
printf '%s\n' '{"sender_id":"alice","recipient_id":"bob","amount_kopecks":15000}' \
  > "$pending/transfer.json"

curl --max-time 1 -fsS http://localhost:8000/transfers \
  -H "Idempotency-Key: $(cat "$pending/key")" \
  -H 'X-Wallet-Lab-Timeout: true' -H 'Content-Type: application/json' \
  --data-binary "@$pending/transfer.json"
```

Первый запрос завершится по таймауту. Чтобы имитировать перезапуск, откройте новый терминал и присвойте переменной `pending` путь, выведенный предыдущей командой. Повторите запрос из сохранённых файлов.

```sh
curl --max-time 1 -fsS http://localhost:8000/transfers \
  -H "Idempotency-Key: $(cat "$pending/key")" \
  -H 'X-Wallet-Lab-Timeout: true' -H 'Content-Type: application/json' \
  --data-binary "@$pending/transfer.json"
curl -fsS http://localhost:8000/wallets
curl -fsS http://localhost:8000/wallets/alice/history
```

У Алисы останется 85 000 копеек, у Боба будет 40 000. В истории Алисы появится один перевод с ID из ответа на повторный запрос. Следующие повторы вернут то же тело ответа. По умолчанию задержка выключена. При включённом деморежиме сервер ждёт пять секунд только при первом успешном запросе с демозаголовком.

Таймаут означает, что клиент не получил подтверждение. Сервер мог зафиксировать перевод до закрытия соединения. Мобильный клиент показывает «Не удалось подтвердить статус» и позволяет повторить сохранённый запрос с исходным ключом. Новый ключ означает отдельный перевод.

## Спорный перевод и возврат

Отправитель может подать обращение по завершённому переводу. Тестовый оператор одобряет или отклоняет его с обязательной причиной. Одобрение переводит выплату в ожидание исполнения. Отдельный запрос создаёт полный обратный перевод или фиксирует нехватку средств. Демо доступно в Swagger UI с тестовыми заголовками ролей.

## Архитектура

Зависимости бэкенда направлены от `api.py` и `disputes.py` к `services.py`, затем к `domain.py`. Домен проверяет списание и определяет переходы обращения и выплаты. Сценарии вызывают эти правила через интерфейсы хранилища в рамках одной транзакции. `postgres.py` выполняет SQL и преобразует строки в модели домена. На HTTP-границе преобразуются запросы и ответы, а блок `with connect()` задаёт границу транзакции. Демозадержка начинается после коммита.

В `mobile/shared/src/commonMain` пакет `application` содержит модели, восстановление незавершённого перевода и состояние экрана в `StateFlow`. Пакеты `network` и `persistence` преобразуют HTTP и файловый JSON в модели приложения. Пакет `ui` отображает состояния перевода и передаёт действия контроллеру. Android и iOS предоставляют сетевые движки и атомарные файловые операции.

Приложение хранит один незавершённый перевод в приватном JSON-файле с атомарной заменой. На Android используется `AtomicFile`, на iOS — атомарная запись Foundation. Для одной небольшой записи достаточно файла. Приложение сохраняет его до первого POST, поэтому запись переживает завершение процесса. При неопределённом исходе запись остаётся на диске, а новые переводы недоступны до подтверждения результата. Кнопка **Проверить статус** отправляет исходное тело запроса и ключ без заголовка демозадержки. После получения окончательного результата приложение удаляет запись и обновляет баланс и историю.

FastAPI проверяет входные данные и отправляет запросы в PostgreSQL через Psycopg. Каждый перевод выполняется в одной транзакции с уровнем изоляции Read Committed.

1. Приложение записывает ключ идемпотентности и параметры запроса в `transfer_requests`. Благодаря первичному ключу конкурентный запрос с тем же ключом ждёт завершения первой транзакции. После её коммита новый SELECT видит исходные параметры и позволяет получить запись перевода или сохранённый отказ.
2. Запрос `SELECT … FOR UPDATE` блокирует строки обоих кошельков по порядку их ID. Если два запроса с разными ключами расходуют один остаток, второй ждёт, а затем читает обновлённый баланс. Если после первого списания денег недостаточно, второй запрос сохраняет отказ `insufficient_funds`. Единый порядок блокировки защищает от взаимной блокировки при встречных переводах.
3. Приложение записывает перевод и две проводки со знаком, обновляет оба баланса и фиксирует транзакцию. Запись перевода, связанная с ключом, хранит исходный результат. Неожиданная ошибка базы откатывает все эти изменения вместе. Задержка HTTP-ответа начинается после коммита и закрытия соединения с базой.

Документация PostgreSQL об [уровне изоляции Read Committed](https://www.postgresql.org/docs/17/transaction-iso.html) и [блокировках строк](https://www.postgresql.org/docs/17/explicit-locking.html).

## Интеграционные тесты

Запустите чистые правила из `backend/` командой `python -m pytest -q tests/test_domain.py`. Этим тестам не нужна база данных.

```sh
docker compose up -d --wait db
docker compose run --build --rm \
  -e TEST_DATABASE_URL=postgresql://wallet:wallet@db:5432/wallet \
  api python -m pytest -q
```

Для каждого теста создаётся отдельная схема, которую тест удаляет после завершения. Набор запускает настоящий HTTP-сервер, проверяет сохранённые остатки и проводки и отслеживает блокировки PostgreSQL, чтобы подтвердить одновременное выполнение запросов. Для запуска с локальным PostgreSQL установите зависимости из `backend/requirements-test.txt`, перейдите в `backend/` и выполните `TEST_DATABASE_URL='postgresql://…' python -m pytest -q`, подставив свою строку подключения. Роли тестовой базы нужно право на создание схем.

Из `mobile/` запустите `./gradlew :shared:testAndroidHostTest` для общих тестов на JVM или `./gradlew :shared:iosSimulatorArm64Test` для того же набора на iOS Simulator.

На симуляторе iPhone 18 Pro (iOS 27.2) проверили сборку и запуск, загрузку кошелька из локального API и отображение подготовленной незавершённой операции после перезапуска. Общие тесты на iOS проверили повтор запроса и очистку записи. Полный сценарий через интерфейс проверяли на Android. Физические устройства iOS в проверку не входили.
