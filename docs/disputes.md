# Спорный перевод и возврат

[Диаграмма BPMN для просмотра](disputes.svg) · [Модель BPMN 2.0 для редактора](disputes.bpmn)

## Роли

| Роль | Действия |
| --- | --- |
| Отправитель | Подаёт одно обращение по своему завершённому переводу и читает его статус. |
| Тестовый оператор | Читает обращение, одобряет или отклоняет его с обязательной причиной, отдельно запускает исполнение и при необходимости повторяет попытку. |
| Wallet Lab | Применяет правила процесса, блокирует кошельки и атомарно проводит полный обратный перевод, когда у исходного получателя достаточно виртуальных средств. |

Для MVP разрешён один спор на исходный перевод, включая отклонённые обращения. Обратная операция не может стать предметом нового спора. Сумма возврата равна сумме исходной операции и вычисляется сервером. Правила учебные. Процесс работает с виртуальными рублями.

## Переходы статусов

| Действие | Обращение | Выплата | Деньги |
| --- | --- | --- | --- |
| Отправитель подаёт обращение | — → `submitted` | — → `not_requested` | Без изменений |
| Оператор отклоняет с причиной | `submitted` → `rejected` | `not_requested` → `not_applicable` | Без изменений |
| Оператор одобряет с причиной | `submitted` → `approved` | `not_requested` → `pending` | Без изменений |
| Оператор запускает выплату, денег недостаточно | `approved` | `pending` или `awaiting_funds` → `awaiting_funds` | Без изменений, возвращается HTTP 409 |
| Оператор запускает или повторяет выплату, денег достаточно | `approved` | `pending` или `awaiting_funds` → `executed` | Отдельный перевод от исходного получателя к отправителю |
| Оператор повторяет уже исполненную выплату | `approved` | `executed` → `executed` | Возвращается тот же ID обратной операции |

Решение оператора окончательное. Точный повтор решения с той же причиной возвращает текущее состояние. Изменение решения или причины после рассмотрения возвращает HTTP 409. Точный повтор подачи возвращает существующее обращение, а изменение текста после подачи возвращает HTTP 409.

## Демонстрация через API

Откройте [Swagger UI](http://localhost:8000/docs) локального API. Тестовые заголовки позволяют переключать роли и подходят только для локального симулятора.

| Метод и путь | Заголовки | Тело |
| --- | --- | --- |
| POST `/transfers/{transfer_id}/disputes` | `X-Wallet-Lab-Role: customer`, `X-Wallet-Lab-Wallet: alice` для перевода от Alice | `{"reason":"Перевод оспорен"}` |
| GET `/disputes/{dispute_id}` | Заголовки отправителя или `X-Wallet-Lab-Role: operator` | — |
| POST `/disputes/{dispute_id}/decision` | `X-Wallet-Lab-Role: operator` | `{"decision":"approved","reason":"Проверка завершена"}` или `rejected` |
| POST `/disputes/{dispute_id}/refund` | `X-Wallet-Lab-Role: operator` | — |

Создайте перевод Alice → Bob. Подайте обращение по ID перевода, скопируйте ID обращения, одобрите и сверяйте балансы перед отдельным вызовом выплаты. После выплаты история обоих кошельков содержит исходную и обратную операции. В ответе обращения `refund_transfer_id` указывает на обратную операцию.

В PostgreSQL исполнители одного обращения блокируют одну строку обращения через `FOR UPDATE`. Первый исполнитель проверяет и блокирует оба кошелька в том же порядке, что и обычный перевод. Изменение остатков, две проводки, новая операция и переход выплаты в `executed` фиксируются вместе. Следующий исполнитель видит сохранённый результат. При недостатке средств коммитится только `awaiting_funds`, поэтому попытку можно повторить после пополнения кошелька обычным переводом.
